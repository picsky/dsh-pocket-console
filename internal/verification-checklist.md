# 真机验证清单

给维护者一次跑完用。每条写了**怎么验**和**期望结果**，以及**哪一条不对意味着什么**。

准备工作：真实租户上绑定，`delaySeconds` 设 **120**（方便看倒计时），电脑一台 + 手机一台。

---

## A. 优先侧（#9、#15、#16 三处新逻辑）

### A1. 桌面答审批 → 回到桌面优先
1. 让 agent 触发一个审批，**在桌面**答掉它。
2. 期望：日志出现 `back to desk priority`；此后新请求会等满 120 秒才发手机。

### A2. 手机答 → 手机优先，且立即生效
1. 让一个审批等到发到手机，**在手机**答掉。
2. 期望：日志 `switched to phone priority`；此时再触发一个审批，**立刻**到手机（不等 120 秒）。

### A3. 桌面输入框打字 → 回到桌面优先（**新增，最要紧**）
1. 先做到 A2（手机优先）。
2. 回电脑，在**输入框发一条消息**，随便说什么。
3. 期望：日志出现 `back to desk priority`；此后新审批会等满 120 秒。
4. **这条不对意味着**：`rpcId` 字段没有按 0015 的假设出现 → 见下面 D 节。

### A4. 从手机发指令 → **不**误判为人在桌面（**A3 的反面，两条合起来才算证明**）
1. 做到 A2（手机优先）。
2. 在**手机**上从结果卡回复一条指令。
3. 期望：**仍然**是手机优先；接下来触发的审批仍然立刻到手机。
4. **这条不对意味着**：判据太宽，从手机点一下卡就把手机优先撤销了。这是比原 bug 更糟的方向。

### A5. 只开着页面 → 不回退（有意排除）
1. 做到 A2（手机优先）。
2. 让电脑页面开着，**什么都不做**，等一分钟。
3. 期望：**仍然**手机优先。
4. **这条不对意味着**：某个"页面在轮询"的信号被当成了人在桌面。

### A6. 回到桌面时，把专享时间还给"跳过"了它的请求
1. 手机优先状态下，让一个审批到达（此时等待时间为 0，卡应当立刻发出）。
2. **在卡发出之前**回桌面答掉另一个请求（这一步在真机上很难卡准窗口，**预期成功率低**）。
3. 期望：那个请求改按 120 秒等待。
4. **注**：这条窗口在代码里只有一个事件循环轮那么宽，**真机上验不到是正常的**，不必因此认为有 bug。本地已用变异验证覆盖。

## B. 卡片行为（#9）

### B1. 活动卡：只改不发
1. 手机优先，让 agent 跑一个长任务。
2. 期望：手机上出现一张活动卡，状态/轮次/已跑时长/实时输出在动。
3. **重点看**：手机**不响**、聊天列表**不出现新消息**、那条会话**没有新增未读红点**。
4. **重点看**：250 ms 的更新节奏是否顺滑，日志里**不出现**"活动卡刷新失败"。
5. **这条不对意味着**：编辑其实会通知 → 整个活动卡形态的前提不成立，必须重新设计。

### B2. 冻结卡
1. 让 B1 的任务跑完。
2. 期望：标题变**灰色**、状态 `已结束`、出现可展开的"本次执行过程"、**没有任何可点的东西**。
3. **重点看**：灰标题是否真的"一眼是历史"；展开后内容可读吗；手机上会不会太长、要不要滚动。

### B3. 桌面优先时不发活动卡
1. 在桌面优先状态下跑一个长任务。
2. 期望：手机上**没有**活动卡（桌面看得见，不该打扰）。

## C. 结果与通知（#10 的结论）

### C1. 同一条会话里连续"审批 → 结果 → 审批"
1. 让一条会话依次经历这三种。
2. 期望：**每一次都是一条新消息**（都能让手机响），**不是**把旧卡改写。
3. **这条不对意味着**：有某条路径在静默改卡，需要重新查。

### C2. 结果卡之后**不该**再有新任务卡（[0019](../docs/decisions/0019-the-next-task-rides-the-result-card.md) 之后）
1. 手机优先状态下让一轮跑完。
2. 期望：**只有**一条 `DSH 结果`，开新任务的表单**就在它上面**。
3. **反例**：又冒出一条 `DSH 新任务` → 0019 没生效，或某处还在调旧的独立卡片路径。
4. **在桌面优先时**重复：期望只有 `DSH 结果`，而且它上面**也没有**开新任务的表单
   （桌面自己能开，不需要手机递控件）。

### C3. 结果卡能不能看到"这一段做了什么"（**本轮重点**）
1. 让 agent 跑一轮**先给方案、再几条确认**的任务（例如"先列个三步计划再执行"）。
2. 期望：`DSH 结果` 卡上有一个可展开的折叠面板，标题「思考过程」。
3. **展开它**，期望看到：**方案的开头**（你问的那份东西）**和这一段的结尾**（它停在哪）。
4. 让方案**很长**（几十步）：期望头尾都在，中间有一段写着「中间省略约 N 字节」。
5. **这条不对意味着**：`readRun` 没接到事件（第二个 firehose listener 没跑），或者头尾取舍失效。

### C4. 桌面优先期间跑的轮次也要有这段过程（**新增**）
1. **桌面优先**状态下让一轮跑完（不要先接管手机）。
2. 期望：结果卡上**同样**有那个折叠面板——run 记录不再依赖是否发过活动卡。
3. **这条不对意味着**：run 记录仍然挂在活动卡上，P0 没有真正生效。

### C5. 手机接管后的第一个任务有记录（**新增，这是修掉的 bug**）
1. 先在**桌面优先**下让一轮跑起来。
2. 在手机上答掉一个审批（进入手机优先）。
3. 期望：**这一个**任务就有活动卡，并且它跑完后结果卡上有那段过程。
4. **这条不对意味着**：`onPriority` 的枚举没生效（老行为是"下一个 session 事件才建卡"，而那个事件可能就是它最后一个）。

## D. #11 从手机开新任务

### D1. 结果卡上的表单能真的开起来
1. 在 `DSH 结果` 卡**下面那个**输入框里写一句话，提交。
2. 期望：答案和「思考过程」都还在，末尾多一行「**已开新会话** · <工作区>」，控件消失；
   **新会话真的开始跑**；它的结果照常回到手机。
3. **重点看**：新会话的工作区**是不是那个会话原来的工作区**（不是部署默认目录）。
4. **这条不对意味着**：`sessionController.create({ cwd })` 的行为与读到的实现不一致。

### D4. 新会话在网页端**要归到那个项目下**，不是「未分组」（[0020](../docs/decisions/0020-a-phone-started-session-joins-its-workspace.md)，**这条曾经是 bug**）
1. 让网页端**保持打开**，在手机上从一个属于某项目的会话开一个新任务。
2. 期望（**先别刷新**）：那个项目的会话数**当场就多一个**——工作区控制器会广播，不需要手动刷新。
3. 再**刷新页面**确认：它在该项目下，**不在「未分组」**。
4. **反例**：它出现在「未分组」→ 说明创建时仍然只给了目录没给工作区，0020 没生效。
5. 万一落到未分组，日志里应有 `要继承的目录不属于任何工作区` 或 `新会话没能挂进工作区` 之一，
   并且**任务本身仍然跑起来了**（这是刻意的兜底，不是第二个 bug）。

### D5. 旧孤儿会话**不在**自动修复范围内（确认边界，不是缺陷）
1. 看 D4 修复**之前**开的那些会话。
2. 期望：它们**仍然**在「未分组」里。修好之后新开的才归位；旧的要么手工拖，要么另做一次性补救。
3. 若期望落空（旧会话被自动改了位置）→ 说明有我没写进去的写入，需要重新审。

### D2. 开完新任务后优先侧**没有**被误判
1. 做到 D1。
2. 期望：仍然手机优先（A4 的同一性质，但走的是 #11 那条路径）。

### D3. 观感
1. 看结果卡上新任务那一段的引子、输入框、以及按下后的收尾。
2. 期望：一眼能看出"上面是结果、下面这段是另开一个会话"，不像在手机上编辑代码。
3. 若两个输入框分不清 → 见 G2，那是同一条判读。

## E. 尺寸与平台口径（**我在这台机器上验不了**）

### E1. 密集引号的卡片
1. 让 agent 跑一条输出里**大量引号和反斜杠**的命令（打印 JSON、`cat` 一个源码文件）。
2. 期望：卡片**正常送达**；日志里**不出现**"卡片被判定为超出体积上限，按一半长度重投一次"。
3. 如果**出现**了那条日志：说明平台量的是更严的那一层 → 需要把 **32 KB** 的预算再下调。
   （注意：预算的"32 KB"是按**转义后的请求体**计的，与 `budget.js` 的常量同名同义，改这里就要改那里。）
4. 如果**很长的中文**卡被截断得比预期早：说明预算取小了 → 可以放宽。
   （实测折算：这类中文约 **2.87 计价字节/字**，所以 32 KB ≈ 11,400 字；一个 60 步计划 ≈ 4.6 KB。）

### E2. 那条悬了很久的小问题
**你上次测卡时，飞书会话列表里的预览文字变了吗？**
这一条能定掉 `config.summary` 那个"待验证"（它能否自定义列表预览）。

## G. 卡片数量：一次运行到底几条消息（[0019](../docs/decisions/0019-the-next-task-rides-the-result-card.md)）

### G1. 数一遍通知
1. 让手机持有优先侧（先在手机上答掉一张卡），然后在桌面开一轮**会跑一会儿**的任务。
2. 数这一次运行总共响了几次、出现几条消息。
3. 期望：**2 条 / 2 次通知** —— `DSH 执行中`（create）、`DSH 结果`（create）。
   不该再有单独的 `DSH 新任务` 卡。**3 条以上就是没生效。**

### G2. 结果卡上两个输入框分得清吗（这条只能靠眼睛）
1. 打开那张结果卡。
2. 期望：一个框是"回复这条消息"用的，另一个在「或者，在**新会话**里开下一段」下面、写的是
   **"新会话要做什么？"**。
3. **判读**：如果两个框看起来一样，或者你不知道该往哪个里打字 → 引子不够清楚，
   0019 的"重开条件"之一成立，要回来改文案。
4. 顺手验一下**填错框**不会出事：往回复框里写"接着做"，往新任务框里写别的，分别提交，各只应发生
   一件事。

### G3. 用完开新任务之后，答案还在不在
1. 在结果卡的新任务框里写一句、提交。
2. 期望：卡片**不消失、也不只剩一句话**——答案和「思考过程」都还在，最后多一行
   「**已开新会话** · 工作区」，所有输入框都没了。
3. **反例**（就是这次修的 bug）：卡片变成只剩"已开新会话"一句，答案没了 → 立刻反馈。

### G4. 回复之后，答案还在不在
1. 在结果卡的回复框里写一句、提交。
2. 期望：答案和「思考过程」还在，末行变成「**已收到指令**，已排入该会话。」，回复框消失，
   「回复这条消息」那句话也一起消失。
3. 反例：整张卡被换成"已收到指令"一句 → 这就是 [0019](../docs/decisions/0019-the-next-task-rides-the-result-card.md)
   里记的那个既有缺陷回来。

## H. 常驻状态板（**设计已写，代码未动**，见 [0018](../docs/decisions/0018-the-status-board-is-a-pinned-card.md)）

**前提未验证：卡片被交互过之后到底还能不能编辑。** 这条决定状态板能不能带控件。先验它。

### H1. 交互冻结（**先做这条**）
1. 插件发一张**带按钮**的卡（或任何审批卡）。
2. 点那个按钮，**然后**让插件去 `patch` 同一张卡（改标题即可）。
3. 期望 / 判读：
   - `patch` 返回 `code!=0` → **卡片被交互即冻结**。状态板必须无控件（0018 的论断成立）。
   - `patch` 返回 `code=0` **且手机上文字真的变了** → 冻结规则不存在，状态板可以带控件，
     0018 应重开。
   - `patch` 返回 `code=0` **但手机上没变** → 最坏的情况：**静默失败**，插件会以为改成功了。

> ⚠️ **做这条之前先读 `internal/boundaries.md` 的"那个测不出来的实验"。** 第一次尝试失败，因为探针
> 每 4 秒改写一次、**把自己的按钮覆盖掉了**，于是"45 次编辑都成功"被误读成"用户还没点"。
> 正确顺序是：**先发一张不再改动的卡 → 请人点 → 点完再开始改写。**
>
> 顺带记住：V2 里按钮是**裸 `button`**，`{tag:'action', actions:[…]}` 已被移除（`230099`）。

### H2. 置顶卡在手机上的观感（产品前提，插件测不到）
1. 把一张卡置顶。
2. 看：是一条横幅、还是一个可点开的入口？要不要点开才看得到内容？来新消息会不会把它顶掉？
3. 期望：**不点开就能看见关键状态**。若必须点开才看得见，状态板的价值要重新评估——
   它就没比"多一条消息"好多少。

### H3. 置顶之后再编辑，置顶是否保留
1. 置顶一张卡 → `patch` 它 → 刷新/重进对话。
2. 期望：仍然置顶，且内容是新的。

### H4. 孤儿卡
1. 置顶一张卡 → 清掉插件的持久化状态（等价于换机/清 profile）→ 重启 dsh。
2. 期望：插件**不知道**那张卡的存在（读侧全堵），会再发一张新的并置顶。旧卡留在置顶列表里，
   只能**人工取消**。这是 0018 明确接受的代价——确认它至少不会让插件报错或卡住。
