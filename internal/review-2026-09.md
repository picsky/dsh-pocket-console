### R6 为什么只加"计数"、不加"警告"

从进程内部看，**缺 `rpcId` 和一个真的在手机边的人是不可区分的**——两者都是"一条人类消息，旁边什么都没有"。所以"连续 N 条没有 rpcId 就警告"会和真实情况冲突：人越常用手机，误报越多。

改成让**事实可见**：进程内第一条人类消息带 `rpcId` 时说一句"判据生效了（此前有 N 条不带）"；第一条不带时也说一句，并说明这**本身不说明判据坏了**。于是"这个插件怎么越来越爱打扰我"可以对着日志核实，而不是靠猜。同一处还加了"我们订阅了哪些事件名"的启动日志——那是按钮失效时唯一能对比的两个字符串。

### 修 R4/R5 时，那条既存测试抓出了**我自己的**一个 bug

我为了"别在等待重试期间自旋"，把 flush 里 `(record.retryAt ?? 0) > at` 那一支的 `requeue = true` 去掉了。**那是真 bug**：重试**没有自己的定时器**，那个 requeue 正是失败之后唯一会把 flush 叫回来的东西。去掉之后，发送失败的卡**再也不会重试**，而且**没有任何报错**——唯一征兆是一条既存用例超时。

我在这上面绕了很久，因为我在**猜**而不是在**看**。真正解决的是把 flush 的判定逐次打出来，看见失败之后**再没有任何 flush 发生**。教训与探针事故同源：**先让事实可见，再推理**。现在的代码把这点写进注释，并说明"这不是可以省掉的优化"。

### R8：修法在算术上必然，但我没能验证它

`forgetColdest` 原本**跳过每一个还有 timer 的 track** 然后收工——所以"全部在等待"时它一条也不淘汰，这个 bound 就不是 bound。改法是**降级为顺序**（空闲优先，其次最旧），而不是豁免。

但我在本机**造不出"全部在等待"**：驱动 400 个会话，窗口设 20 ms 与 30 s 得到**同一个结果（144 条）**，也就是两种配置下走的都是"空闲"那一支。所以：

- **逻辑上必然**（旧代码对有 timer 的 track 是硬跳过的，这是纯算术）；
- **运行时未验**——我没有让测试声称它验过。测试改成断言**它确实能证明的**（容量守住、约一半存活），并在注释里写明未覆盖的那条分支。

两次**无效的负向对照**也记在这里：我以为对照失败就是"测试没意义"，其实是**替换没匹配上**。而我的诊断输出一直被子进程和测试运行器吃掉，转成**写文件**才拿到数字。教训与前两次同源：**先让事实可见，再推理**。

### 评审自身的两处更正

1. **R5 的措辞**：我原先写"结果卡折叠是 32 KB 的一半"。**错**——一半是**活动卡**的
   `PROCESS_BUDGET`（`activity.js:80`），结果卡的 `runGroups` 拿的是**完整** `CARD_TEXT_BUDGET`
   （`results.js:366`）。写 README 时实测才发现，已按完整值写进文档。
2. **R3 的严重度**：我原先把它归在"无界增长"里。修的过程中看清它的真实形态是
   **两个容器描述同一个生命周期**（notice 与 view），那条泄漏恰好发生在两者短暂错位的一刻。
   所以修法不是"加个上限"，而是**取消第二个容器**——这也让 R15 的那一半自然消失。

## 角度 1：状态机与生命周期

### R1（S1，已验证）**"已发送"是在发送结果未知之前答应的**

```js
// results.js:815-820
notices.delete(id)
void store.remove(id)          // 持久化里也删了
void send(agent, text, notice) // ← 不 await
return { toast: messages().sent, accepted: true }
```

而 `send()` 的失败只记一条 warn（`results.js:868-870`）。两条真实失败路径：

1. `await import('@deepseek-ai/dsh-llm')`（`results.js:832`）在契约解析失败时 reject；
2. `agent.followup(...)` 抛错（例如 811 行的 `agents.get()` 之后、调用之前会话被回收）。

**后果**：使用者收到"已发送给 agent"，而指令**不存在于任何地方**——rid 在内存和持久化里都已删除，卡片上的输入框也已被替换成"已收到指令"。**没有任何重试入口**，因为防御重复提交的机制恰好就是让它无法重试的东西。人类会以为下一步已经派下去了，于是不再管。

**为什么是 S1 而不是 S2**：这不是"少一张卡"，是**人被骗**。而且它发生在唯一一条"手机推进工作"的路径上。

**修好的判据**：`handleAction` 变成 `async`，在**知道发送结果之后**才给 toast；发送失败时**把 notice 放回去**并给一条诚实的 toast。代价要明确：`send()` 的同步段（动态 import + `followup`）必须留在平台的 3 秒回调预算内；真要超时，宁可让使用者看到"没发出去、再按一次"，也不要看到假的"已发送"。

### R3（S2，已验证）`views` 无上限，且有一条路径永不释放

`views` 是"这张结果卡发出时的样子"，用来在改写时保住答案和「思考过程」。全仓 8 个容器里**只有它没有容量上限**。清理点只有三处：`retract()`（639）、回复改写（851）、`aftermath()`（670）。

而 `retire()`：

```js
// results.js:701-715
if (notice.handle === undefined) continue   // ← 卡片还在途时跳过了 retract
retract(notice.handle, headline, notice.workspace)
```

`notice.handle` 在 `deliver` 尚未返回时是 `undefined`，此时 `continue` 跳过了那个唯一的清理点；等投递完成写入 `views` 时（433），`notices.get(id)` 已是 `undefined`（刚才删的），所以**这条 view 此生再无改写点**。一条 view 装着整张卡的正文（可达 32 KB）。

**触发条件**：新结果取代旧结果，发生在上一条卡投递完成之前。默认冷却为 0，紧挨的两个回合就能撞上。

**修好的判据**：把 view 挂在 notice 上（`notice.view`），让"notice 没了"和"view 没了"是同一件事——而不是靠三个函数各自记得删。这同时消掉 R15 的一半。

**已修（#40）**：`views` 这个 Map **整个删掉了**，`VIEW` 成了 notice 自己的属性，四个引用点收敛到一个 `cardOf(handle)`（按消息在活 notice 里找）。写入点加了守卫——notice 已经不在就不记 view，因为那时已经没有东西会来改写它，正是当初泄漏的那一步。

**并且加了一条守形状的测试**（`tests/result-view-ownership.test.mjs`）：它读 `results.js` 的源码，断言"不存在第二个装卡片的容器"、并且"每条改写路径都走同一个 `cardOf`"。**这看着不像常规测试，但理由充分**：这条 bug 的**行为表现全是对的**——卡照常送达、照常改写、答案和折叠都在，没有任何行为用例会失败；错的只是留了一份没人会释放的副本，而它唯一的外部征兆是内存随运行次数增长。行为用例在结构上就抓不到它。**负向对照**：把 `const views = new Map()` 加回去，这条立刻失败并指名道姓。

### R4（S2，已验证）发送失败的重试**无终止**

```js
// activity.js:506-514
.catch((error) => {
  record.sending = false
  record.retryAt = now() + RETRY_MS
  record.dirty = true              // ← 5 秒后再来一次，永远
})
```

而时钟（`531-538`）每 5 秒把每个未 settled 的记录标脏。uuid 让重试**安全**，但没让它**有限**。通道长期不可用时，就是每 5 秒一条警告，直到进程结束。

**修好的判据**：加尝试上限；到顶之后**放弃并留下痕迹**（`log.error` + 把卡置为最终态），而不是无限安静地重试。

### R5（S2，已验证）冻结卡的**最后一次改写失败后永不补写**

时钟只碰未 settled 的记录：

```js
// activity.js:535
if ([...activities.values()].some(record => record.handle !== undefined && !record.settled)) touch()
```

`turn/end` 把 `settled` 置真之后，若那一次改写失败（只是 `log.warn`，`517-518`），**没有任何东西会再试**。读者就此看着一张写着"运行中"的卡片，而那一轮早跑完了。

**修好的判据**：改写失败要重试（至少一次），或者明确接受"最后一笔可能丢"并**在卡上说明它可能不是最新**。后者更诚实，也更便宜。

### R8（S2，已验证）`forgetColdest` 可成为空操作

```js
// results.js:252-261
if (tracks.size < TRACK_CAPACITY) return
const idle = [...tracks.entries()].filter(([, track]) => track.timer === undefined)
```

`trackOf` 在**知道它是否空闲之前**就插入记录。若大量会话同时持有冷静窗口，`idle` 为空 → 一条也不淘汰 → `tracks` 无界，而**别处没有任何东西退掉 track**。

**修好的判据**：空闲集合为空时也要能腾位置（例如按 `touched` 强行淘汰最冷的那条，哪怕它还有计时器——届时顺带清掉它的计时器）。

### R12（S3，已验证）活动卡淘汰留下孤儿卡

`activities` 满 64 时直接 `delete` 最冷记录，**不处理它的 `handle`**（`activity.js:158`）。该会话的下一个事件看到 `handle === undefined`，于是**新发一条**——一次运行两条消息。注释（`136-143`）与测试（`activity.test.mjs:791-793`）都声称这被防住了，但测试只断言了"记录数是 64"，没断言"不会多一条消息"。

代价有界（≤64 个记录 × 每记录很小），所以我放 S3 而不是 S2。**修好的判据**：淘汰时把那条记录的 handle 记住（或直接不淘汰有 handle 的记录），并补一条用例：驱动 65 个会话，对最冷的那个再发一个事件，断言 `observed.created` **没有**增长。

### R13（S3，已验证）`close()` 不摘 `abort` 监听

`escalation.js:327` 注册 `record.onAbort`，唯一的摘除在 `release()`（288）里，而 `close()`（638-645）只清计时器和 `open`。在途请求的 signal 上会一直挂着监听（以及 `settle`/`released` 的 resolver）。

## 角度 8：文档与代码一致

### R2（S1，已验证）**对外发布的 README 在说我们已经证伪的数字**

`README.md:100` / `README.zh-CN.md:100` 三处冲突：

| README 说 | 本仓库的结论 |
|---|---|
| 请求体上限 **30 KB** | **实测 131 KB 通过、164 KB 被拒**（`internal/boundaries.md:66` 已写明"30 KB 是错的"） |
| 文本限制在 **4.5 KB** | 代码 `CARD_TEXT_BUDGET = 32 KB`；结果卡折叠是它的一半 = **16 KB** |
| 约 **1500 个汉字** | 实测中文 **51,000 字通过**；16 KB 预算下汉字远不止 1500 个 |

`internal/verification-checklist.md:137` 也在说"把 4.5 KB 再下调"——同样过期。

**为什么是 S1**：README 是唯一对外发布的说明，它给出的上限**比真实能力低一个数量级**，于是读者以为长计划一定会被砍——而这个插件最花力气的事恰恰是把长过程保住。更贵的是：**内部文档已改正、外部文档没有**，两份数字并存本身就是下一个错误结论的温床。

**修好的判据**：README 两语、`budget.js` 常量、`internal/boundaries.md` 实测表**三者一致**，并且有检查防漂移（我提议：让 README 引用常量所在的文档，或让文档里的数字由脚本从常量渲染）。

### R7（S2，已验证）**没有一处守整张卡的请求体**

实测被拒的是**请求体 164 KB**；代码守的是**文字字节**（32 KB）与**元素个数**（120）。元素多但每个很短的卡片，文字远不到 32 KB，请求体却可以很大。`tests/result-run.test.mjs` 那条"仍然放得下"只覆盖**结果卡**，且断言的是 `< 131 KB`——正好是**被接受**的那个值，不留余量，也不覆盖审批/提问/活动三类卡。

**修好的判据**：对 `renderCard` 的**输出 JSON** 设一个字节预算（而不是对文字），四类卡各一条用例，并**记录实测依据**（被拒值 164 KB 与接受值 131 KB 之间取一个有 margin 的数）。

### R15（S3，已验证）重复维护的实测表 + 标题解析算两遍

- `budget.js` 的文档表与 `internal/boundaries.md` 的表记同一批数字，各自手写。这次一致是运气。
- `work.js:132` 的 `mergeInto` 重新 `workspaceOf(session)`，而 `view.title` 已由 `results.js` 算过一遍——`identity.js` 自己的规矩就是"改写时不要重读"。后果有限，但是那条规矩的一个漏洞。

## 角度 2：平台契约

### R9（S3，已验证）发送没有超时

```js
// providers/feishu.js:891-911
const response = await transport.client.im.message.create({ ... })
return response?.data?.message_id
```

凭据检查有 `withDeadline`（`196-230`），**投递没有**。SDK 的 promise 若永不 settle：`results.js` 永远不会赋 handle、`store.put` 永远不到达（通知既不活也不持久），而 `activity.js:495` 的 `record.sending` **永久为真**，那张卡再也不会被写。

### R11（S3，已验证）平台"每消息 5 QPS"没有按消息节流

节流是**一个模块级 `refreshTimer`（250 ms）**（`451-455`），而 `flush()` 在**一次同步循环里**给每个脏记录各发一次 `channel.update`（`466-521`）；`touch()`（`524-528`）把**所有**记录标脏。平台限的是"**同一条消息** 5 次/秒"，代码里没有任何按消息的间隔。两次相隔 250 ms 的 flush、或一次 flush 加上前一次尚未返回的 patch，都会把 2 次更新压进 <250 ms。当前实现下最容易命中的是同一条消息连续两次刷新——余量为零。

### R10（S3，已验证）`deliver()` 可能返回 `undefined` 而调用方当成功

```js
return response?.data?.message_id   // 可能 undefined
```

`activity.js:499` 与 `results.js:430` 都会把它当 handle 记下；后果是那张卡再也不能被编辑（`activity.js:489` 视 `undefined` 为"还没发"）或那条通知再也拿不掉回复框。**修好的判据**：没有 id 就是投递失败，让调用方走它的失败路径（含 R9 的超时）。

## 角度 4：测试的意义

我**没有只读断言**，而是做了一个**负向对照**：把刚合并的修复回退成原来的 bug，看测试是否真的失败。

```
✖ a phone-started session is created through its workspace, not a bare directory
✔ a directory no workspace owns is created by directory, and the log says why
✔ a registry that refuses still starts the task, ungrouped
✖ a creation that fails is retried by directory, and prompts exactly once
✔ a deployment with no workspace registry keeps working, by directory
✔ no session controller is reported, and nothing is created
ℹ pass 4  fail 2
```

**正好那两条与 bug 相关的失败，四条兜底路径照旧通过**——说明它们守的是这条 bug，不是顺带过的。（随后已恢复并确认 6/6 绿。）

其余发现：

- **`budget.js` 覆盖比我预期的好**：`messages.test.mjs:71-117` 直接测裁剪的不变量，含"标记比预算还宽"和"预算为 0"两个边界，以及"引号密集串上两种度量会分歧"这个正是当初量错的情形。**不算缺口。**
- **R14（S3，已验证）`routes.js` 的安全关键分支没有单测**：`sameOrigin`（100）、`MAX_BODY_BYTES`（60）、非 JSON、非 POST 都只在运行时生效。e2e 验了**信任栅栏**（未信任 → 401，且对每条路径都验），但**没验同源写拒绝**——而 `sameOrigin` 正是变更类请求的栅栏。这是"安全边界无测试"的标准形态：默认允许、只在跨站时拒绝。
- **R3/R6 这类"多个容器生命周期不一致"的结构，测试结构上是测不到的**：`views` 与 `notices` 是同一个生命周期的两半，却分开记账，而外部只能观察 `trackedSessions()` 一个数。**建议**：给 `results.js` 加一个内部一致性断言式的可观察量（例如 `views.size` 与 `notices.size` 的关系），比再写十条行为用例更能防住这一类。
- **时序**：多数用例用固定的 `sleep`（如 `sleep(1_200)`）等冷静窗口。它们目前稳定，但"等一个固定毫秒数"在负载机器上会翻。`tests/result-run.test.mjs` 里我新加的那条已经改成**轮询到条件成立**，建议同类用例照此办理。
