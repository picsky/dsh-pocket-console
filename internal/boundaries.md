# 边界

**一页纸。** 它存在的唯一目的是让下一个改动**更快做决定**：哪些边界是深思熟虑的、哪些只是碰巧没做。仓库里 `docs/decisions/` 记的是"为什么代码长成这样"；**这里记的是"为什么只做这些、以及为什么不做那些"。**

**防变胖约束**：任何一条，如果读的人不需要它就能做决定，它就不该在这张纸上。要展开的理由请去对应的 decision record，不要抄过来。

内部文档，刻意**不**放进 `package.json` 的 `files`，所以不会被发布。

## 0. 证据三级

这条最有用，所以放最前。**同一场讨论里，两个"看起来显然是结论"的判断都被查证推翻了**——它们之所以能一路流动，正是因为假设伪装成了结论。

| 标注 | 含义 |
|---|---|
| **已验证** | 在本仓库或真实环境**实测**过，或读过实现代码/文档原文确认 |
| **推断** | 从代码或文档推出来的，**没有实测** |
| **待验证** | 只有真机能定，且**失败时可能无声** |

## 1. 边界表（每条一句话理由）

### 做

| | 理由 |
|---|---|
| 桌面优先，手机只做**助手**：推进已有工作 | 手机的价值是**便携**，不是屏幕。做成 dsh web 的移植版会同时输给桌面和原生 |
| 审批、提问 → 卡片 | 这两件事会**阻塞** agent，需要人立刻决定 |
| 一轮跑完 → 结果卡 | 会话停下来了，而"该你了"是一个需要人介入的**决定**，不是状态播报 |
| 长任务 → 活动卡（只改不发） | 长任务期间手机收不到任何东西，而"它还在跑吗、跑到哪了"正是此时唯一的问题 |
| 优先侧跟着人走 | 人一旦在手机上处理过，为一张空椅子等专享时间就是在拖延唯一能回答的那个界面 |
| 从手机开下一个任务 | 长任务跑完时人往往不在桌面，而"开下一个 shard"是**只有手机能及时做**的决定。限当前会话的工作区（[0016](../docs/decisions/0016-the-phone-can-start-the-next-task.md)） |
| 出站长连接 | 不需要公网 IP、域名、隧道，也不开端口 |

### 不做

| | 拒绝它的理由 |
|---|---|
| 不开任何入站监听 | 开了就要面对"从任何地方可连"，那是另一个安全模型。代价是手机只能被动收卡 |
| 不搬 GUI / 不做会话管理（列表、搜索、归档） | 搬界面就要搬工作区、会话、设置、凭据。手机不需要它们就能**推进** |
| 不做休眠会话 | 不活跃的会话没人用得上；做了要连带做生命周期、归档、唤醒，全是为一个不存在的场景 |
| 不选工作区 | 卡片是一份决定的凭证。让它能指定路径，等于丢了手机就能在机器上任意目录跑活（[0016](../docs/decisions/0016-the-phone-can-start-the-next-task.md)） |
| 不把 pin 当状态推送面 | pin 的**写侧**可用（见 §3），但它是"人主动去看"的面，不是推送面：置顶不会替插件叫人。常驻状态板已单列（见 §3 与 [0018](../docs/decisions/0018-the-status-board-is-a-pinned-card.md)） |
| 不用 `open_url` / AppLink / webview | 要我们自己提供一个可访问的网址，等于**开一个端口**，与上一条冲突 |
| 不主动推**状态** | 一个开着的页面或一个忘关的标签页会把"人在手机边"这个真实状态盖掉（[0015](../docs/decisions/0015-desk-presence-is-the-gateways-request-id.md)） |
| 永不自动批准 | **沉默不作数**。插件从不替你决定 |
| 从不改 DSH | 它是 bundle profile 层，只注册在两条已文档化的 waterfall 上。DSH 升级不该弄坏它 |
| 不做迁移/兼容旧版 | 没有维护中的旧分支，版本就是最新发布版 |

| 能力 | 人什么时候需要 |
|---|---|
| 审批卡 | 一条命令等着批准，而我不在电脑前 |
| 提问卡（多问题可逐步答） | agent 要我选，而我只有手机 |

| 活动卡 | 长任务跑着，我只想知道**它还在不在跑、到哪了** |
| 优先侧切换 | 我在手机上处理过一次，接下来别为一个空椅子等 |
| 手机开新任务 | 一个 shard 跑完了，**下一个 shard 得现在开**，而我不在桌面 |

## 3. 外部能力边界

### 飞书

| 约束 | 证据 |
|---|---|
| 卡片请求体上限 30 KB | ❌ **文档这么说，实际不是**。实测：**131 KB 通过、164 KB 被拒**（`230025`）；`patch` 实测 98 KB 通过。**照文档建预算是这次所有"历史总被截断"的根因** |
| 回调须 3 秒内应答（长连接也一样） | **已验证**（文档原文） |
| `im.message.patch`：14 天内、单消息 5 QPS、前后都需 `update_multi:true` | **已验证** |
| **`header.subtitle` 可用，而且必须是对象** | **已验证**（真实租户实测，2026-09-21）：`{ tag: 'plain_text', content }` → `code=0`，手机上**真的多出一行小字**；**裸字符串 → `230099`**（card content 不合法）⇒ 平台**认识并校验**这个字段，**不是** `streaming_mode` 那种"收下但静默无效" |
| **标题与小字都没有硬上限** | **已验证**：标题到 **144 显示列**、小字到 **182 显示列**，全部 `code=0` ⇒ 唯一的约束是**显示**，不是平台 |
| **标题的视觉截断点落在 87 与 144 显示列之间；小字不跨行、超出由平台截断** | **已验证**（使用者真机目视）：87 列的标题没被截断，144 列的被截断；小字过长不换行、由平台截 |
| **`patch` 能改小字**（不只是标题） | **已验证**：`PATCH` 同一个消息换 `subtitle` → `code=0`，手机上跟着变 ⇒ **晚到的会话名补得上** |
| **编辑一张已发出的卡是静默的**——不响、不产生新消息、列表预览不变 | **已验证**（真实租户实测）。**这是活动卡能成立的全部原因** |
| 没有"静默消息"这种东西 | **已验证**（文档原文）。注意力只能靠少发，不能靠关掉 |
| 折叠面板不支持内嵌表单 | **已验证**（文档原文） |
| **元素数上限 200** | **已验证**（真实租户实测）：180 通过、200 被拒（`230099`，`element exceeds the limit`） |
| **正文长度上限** | **已验证**（真实租户实测）：中文 51,000 字通过 / 51,300 被拒；拉丁 120,000 通过 / 200,000 被拒；emoji 20,000 通过 / 40,000 被拒。量的是**解码后的内容**，不是请求体；各类字符阈值不同 |
| **面板 header 不接受对齐** | **已验证**：markdown 与 `div` 上的 `text_align` 被接受，panel header 上的被拒。标题文字本身可点即展开 |
| `hr` 与 `div` 元素可用 | **已验证** |
| 读取已发消息需要 `im:message:readonly` 或 `im:message` | **已验证**：本应用两者都没有，回读被拒（`99991672`） |
| `config.summary` 能否自定义会话列表预览 | **待验证**（文档有，但本地 SDK 类型里没有） |
| pin 的**写侧可用**：置顶、取消置顶、以及**编辑一张已被置顶的卡**全部 `code=0` | **已验证**（真实租户实测，2026-09-20）。⚠️ 此前本文档写"内测、私聊未文档化"并据此拒绝——**那条是错的**，从未实测。置顶不需要任何新权限 |
| pin 的**读侧全堵**：`GET /im/v1/pins` 需 `im:message.pins:read` | **已验证**（`99991672`）。⇒ 插件**列不出自己的置顶**，必须自己持久化 `message_id`。容器一旦丢失（换机、清 profile），置顶卡就会变成孤儿，只能人工取消 |
| `patch` 一张**已被置顶**的消息仍然成功；置顶不冻结内容 | **已验证**（`code=0`） |
| **cardkit 卡片实体**（`POST /cardkit/v1/cards`、流式更新、全量替换、`batch_update`）需要 `cardkit:card:write` | **已验证**：本应用无此权限（`99991672`）。⇒ **流式卡片路线走不通**，除非部署方去补这个权限。`im/v1/messages` 的 `create` 接受 `config.streaming_mode: true` 但**不报错也不生效**（服务端流式更新在 cardkit 侧），所以它是**静默无效**，比拒绝更坏——不可依赖 |
| cardkit 的 `card_id` **不是** `message_id`（校验：`max len is 20`） | **已验证**。它是独立的卡片实体 id，与"发出去的那条消息"是两套生命周期 |
| 表情回应（读/写）需要 `im:message.reactions:*` | **已验证**：本应用没有 |
| schema V2 里按钮是**裸 `button` 元素**放在 `body.elements` 里 | **已验证**（真实租户，三张卡对照）。`{ tag: 'action', actions: [...] }` 这种 V1 容器**已被 V2 移除**：`230099` `unsupported tag action`。插件用的就是裸 button 形状 |
| **表单被提交过的卡片，之后还能继续 `patch`** | **已验证**（真实租户实测）：一张带表单的卡**被人提交之后**仍连续接受改写（90 次全部 `code=0`），且表单控件一直留在卡上。⇒ **"我按的那张卡就地变"可行**（[0021](../docs/decisions/0021-the-card-you-pressed-is-the-one-that-moves.md) 整个建立在这条上） |
| **按钮被按下**之后的改写 | **待验证**——只有"发出时刻"测过，没测过"按下之后再改"。所以：**必须就地变的卡一律用表单**；审批卡/提问卡用按钮，但它们从不需要事后改写。下面的探针事故就是这条没做对 |

#### 那个测不出来的实验（一次真实的探针事故，记下来免得重犯）

想验"卡片被点过之后是否冻结"，做法是发一张带按钮的卡、每 4 秒 `patch` 一次，看用户点完之后
`patch` 是否开始被拒。**结果 45 次编辑全部 `code=0`，于是被读成"用户还没点"。这个读法是错的。**

真正的错误在探针本身：**每次 `patch` 都只发纯 markdown，把按钮覆盖掉了**。第一轮编辑（发出后 4 秒）
之后，卡上就再没有按钮可点——用户看到的正是那张没有按钮的卡，而我把"45 次都成功"误当成"没人点"。

两条教训：

1. **探针不许改掉它自己要测的东西。** 要观测"交互"，就得让控件一直在卡上——观测期间**不要改写**
   那张卡，改用别的信号（另一张卡、日志）来观察。
2. **"没观察到"不等于"没发生"。** 45 次成功只证明"当时没有交互后的改写被拒"，不证明"没有交互"。
   把沉默当成证据，就是这次把错误结论写进结论栏的原因。

正确的做法：发一张**不再编辑**的卡 → 请人点一次 → 点完后再连发 10 次改写，看第一次之后的响应。

**后来这么做了一次，而且探针没有覆盖自己：** 一张**带表单**的卡，每 4 秒改写一次，**每次都把表单原样带着**
（不再发纯 markdown），用户在编辑计数器还在往上走的时候提交了那个表单。结果：**继续改写 90 次全部
`code=0`，卡片上的文字确实在动。** 结论写进上表：**表单提交之后仍可改写**。

**但按钮那一格仍然是空的。** 表单（提交）和按钮（点击）在服务端不是同一条路径，上面那次没有测到按钮。
所以判据不是"交互会冻结卡片"，而是"**我们只在表单上验过**"——需要就地变的卡用表单，别赌按钮。

| `workspaceId` 与 `cwd` **不能同时给**（`gateway/bad-request`） | **已验证**（读实现） |
| 工作区控制器在持久化域变化时**主动广播** `upsert` 给 Web 客户端 | **已验证**（读实现）⇒ 挂载成功时**开着的页面不必刷新**就会显示新会话 |
| `WorkspaceRegistry.resolveByPath(path)` 做 `realpath` 后按字符串匹配；目录无主返回 `undefined`，目录不可解析则**抛错** | **已验证**（读实现） |
| `sessionController.prompt()` 会把调用方 request id 写进消息 source；**其他人类消息路径都不写** | **已验证**（逐个查过。这是桌面判据的基础，见 [0015](../docs/decisions/0015-desk-presence-is-the-gateways-request-id.md)） |
| 该字段**没有任何类型声明**，只存在于运行时的对象上；失效时**静默** | **已验证**（搜遍所有 `.d.ts`）。**这是一处上游依赖风险** |
| 工具结果可达数百 KB，且会话层**没有截断标记** | **已验证**（读实现） |
| 浏览器 composer 的逐题进度够不到（store 是组件私有） | **已验证**（[0012](../docs/decisions/0012-the-desktop-composer-steps-without-the-phone.md)） |
| **`agent.followup()` 排进一个正在跑的会话**，真机上**观察到未兑现** | ⚠️ **现象已验证，机理未明**（2026-09-21 真机）：`followup` 返回 void、不抛错，通知被消费、卡片也变了，但**没有开出那一轮**（`turnOutline` 里没有对应 turn，inbox 事后为空）。对照：**空闲时** `followup` 正常成轮。契约写的是"排成自己的一轮并唤醒 driver"（`followup(input) { this.send(input,'next-turn',true) }`），所以嫌疑在 inbox 的收回路径（轮结束时清掉 / `claim` 走却没开轮），**没有证死**。⇒ 插件在会话 running 时改用 `steer()`（[0023](../docs/decisions/0023-a-reply-into-a-running-session-steers.md)） |
| `agent.steer()` 的契约 | **已验证**（类型原文）："Submit steering for the nearest step. An idle driver starts a turn; a running driver consumes it at its next step boundary." 取消或卸载**可能丢弃**未消费的 steering |
| 会话的**创建头** `session.header` 公开且**始终存在**（`Session` 的一个字段，注释写明"总是存在"）；其中 `origin` 的校验**只接受 `"subagent"`** 这一个值 | **已验证**（读实现：`dsh-session/lib/types/index.js:337-353` 的字段声明、`:55-56` 的校验；本机 82 个会话头实测都写着 `"origin":"subagent"`）⇒ 判"这是不是委派会话"不需要任何状态，插件启动前就存在的会话也判得出来 |
| `session/event` 的第二个参数**就是 `Session` 实例**（firehose `callbackArgs = [this, event]`），因此 `session.header` 在事件处理里直接可读 | **已验证**（读实现；插件早在读 `session.header.cwd` 取工作区名） |
| **子代理的派发提示词以 `{ kind: 'user' }` 送达**，与真人消息同形（只差只有桌面手敲才有的 `rpcId`） | **已验证**（真机会话日志：子代理 `seq 9 source={"kind":"user"}`）⇒ **靠 source 判"这是不是人开的会话"不可能**，这是 #62 的根因 |
| 子代理会话的**第一条事件**是 `subagent/descriptor`（seq 0，早于 `turn/start` 的 seq 5），且属于 session 日志的已知事件类型 | **已验证**（真机会话日志 + `dsh-session` 的 known-event-types 列表）⇒ 若上游有一天不再写 `origin`，这是退路 |
| `fork()` 造出的会话**带 `parentSession` 但不带 `origin`** | **已验证**（读实现：`dsh-session/lib/index.js:1670-1678`）⇒ 判据只能用 `origin`；用 `parentSession` 会把 fork 一起静音，而 fork 是人在用的会话 |

## 4. 渲染政策

**一条判据：这个元素会不会改变你下一句要写什么？**

会 → 留。不会 → 丢。推理与成功过程都不改变你的下一句，所以丢，但**丢了要说明丢过**（否则你无法判断记录是否完整）。

它导出的取舍：

| 元素 | 处置 |
|---|---|
| 人的消息、模型说的话 | **原样保留** |
| 成功的工具调用/结果 | 丢 |
| 失败的工具 | 留一行，**带原因** |
| system 消息、reasoning | 丢 |
| 过程折叠 | **只有冻结的卡**才折 |

### 改写一条已发出的卡：不许弄丢正文

结果卡会在三个时刻被改写（读者回复、被更新的结果取代、过期失效），开新任务的那张也会（用完
之后）。**每一次改写都必须从"发出时的卡"重建，而不是拿一句话把整张脸换掉**——后者会把答案和
「思考过程」一起吞掉，而读者刚回复完、往回滚，正在读的东西就没了。踩过两次（0017 的
`details`、0019 的回复改写），所以这里记成硬规则：

- 改写要保留：答案正文、`details` 折叠、以及**没被用掉的那些控件**。
- 只允许拿走：刚被用掉的那个控件，**以及它那段话**。两件事必须一起做——卡片上留着"或者，在
  新会话里开下一段"却删掉了输入框，和丢掉答案一样是在骗读者，只是更安静。
- 边界记在**答案之后**，不靠比对文案。按句子匹配会在改文案的那天静默失效。
- 拿不准就别改：**找不到"发出时的卡"时宁可不改写**。一句"为什么不能用了"的卡片，比一张丢掉了
  答案的卡片好。

## 5. 失败场景表

每加一个功能，**横着问一遍**："在这个场景下它怎么表现？"

| 场景 | 已定行为 |
|---|---|
| 手机没网 / 通道挂了 | 发卡失败进重试（5 秒退避）；桌面分支仍然权威，调用方继续等桌面 |
| `dsh` 中途重启 | 优先侧是持久的（凭据库）；通知是持久的（`notice-store`）；**活动卡的记录不持久**，重启后那张卡停在原地 |
| 两个会话同时跑 | 每个会话一张卡；活动卡上界 64 个会话，**会话观察态上界 256 个**（`TRACK_CAPACITY`），通知每会话最多一条（回复/被取代/过期即清） |
| 桌面开着但人不在 | **只开着页面不算人在桌面**（[0015](../docs/decisions/0015-desk-presence-is-the-gateways-request-id.md)） |
| 桌面关了人也不在 | 正是本插件存在的场景：等专享时间耗尽后发手机 |
| 审批和结果同时来 | 各自一条新消息，互不覆盖 |
| 连按两下 | 审批：只有settle那次有效，后到的被拒；结果卡：rid 单次使用；新任务卡：用过即收回表单 |
| 一轮里连问两个问题 | 一张卡原地推进（[0011](../docs/decisions/0011-one-question-per-card.md)），**不发新消息**——此时静默正是要的，因为读者正在那张卡上操作 |
| 卡片发出后请求已结束 | 再按会被改写成"该请求已失效"并去掉控件，不再看起来可答 |
| 一段过程长到装不进一张卡 | **放不下时按内容种类依次放弃（合并工具行 → 丢工具行 → 丢人说的那句 → 丢最早的散文），丢了多少标明字节数**（[0017](../docs/decisions/0017-the-result-card-carries-the-run.md)）。不拆成多条消息，因为那是多次通知 |
| 运行发生在桌面优先期间 | 不发给活动卡（桌面看得见），但 **run 记录照记**——结果卡要用它 |
| 运行只以实时片段到达、没有提交消息 | 记录在 `turn/end` 折叠整段流，所以结果卡仍有内容 |

## 6. 已知的、不打算修的

这些是**诚实的缺口**，不是选择。写在这里是为了别被当成 bug 反复报。

- **响应丢了 + 通道不认 `uuid` + 平台已接受** —— 客户端无法解决，会变成第二条消息。
- **run 记录与冻结卡的折叠各有上界**，超出时丢的是**最早**的条目；丢了多少会写在卡上。
- **审批卡不折过程**，它只留一句结论。结果卡**会**折这一段 run（[0017](../docs/decisions/0017-the-result-card-carries-the-run.md)）。
- **一段 run 太长时中间看不到**，只能回桌面——卡片之间不能跳转，也不开网页。
- **镜像回填需要页面开着**，且窗口只有一分钟。
