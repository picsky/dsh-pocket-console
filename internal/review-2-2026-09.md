## 三、逐条详述

### N1（S2，待验证）— #53 的上游依赖：`reason.kind` 并不总是说真话

#53 用 `UNFINISHED_REASONS = {error, max-tokens}` 决定"报错的一轮也发卡"。`onEvent` 里：

```js
if (reason?.kind !== 'completed' && UNFINISHED_REASONS.has(reason?.kind) === false) return
```

`fire` 里：

```js
const unfinished = track.reason !== undefined && track.reason.kind !== 'completed'
if (!unfinished && !isAnswer(track.message)) return
```

**盲区**：若一次工具失败最终以 `reason.kind === 'completed'` 结束——[deepseek-ai/deepseek-harness Discussion #4410](https://github.com/deepseek-ai/deepseek-harness/discussions/4410) 标题即"Silent success: failed tool chain still ends with reason.kind = completed and headless exit 0"——则 `unfinished = false`，此时若最后一条消息无文本（`isAnswer` false，例如失败发生在工具调用后、模型再没有产出文本），**仍不发卡**。这正是 #53 声称要修的场景（"它非常常以调用失败工具的 message 结尾，不携带文本"），却因 reason.kind 的静默误报而漏掉。

- **为什么是 S2 而不是 S3**：这是 #53 的**核心承诺**（报错轮也要能回复）在该上游行为下的失效；且上轮 R6 已经记录"上游契约失效全是静默的"是这类插件最贵的失败模式。
- **修好判据**：真机上让一条工具链失败，观察 `turn/end` 的 `reason.kind`；若确为 `completed`，则 #53 的判定需要另一个信号（例如"最后一条消息带 tool-call 且 `turn/end` 的 reason 不是人为停止"），或至少把"报错但 completed"也视为未完成。待真机确认后定夺。
- **本地无法证**：测试桩里 `turn/end` 的 reason 由用例直接构造（`{ kind: 'error' }` 等），无法复现 harness 的真实分类。

### N2（S2，已验证）— 镜像把 `answer()` 的任意拒绝都当成功上报 applied

`client.js:922-927`：

```js
try {
  void Promise.resolve(pending.answer(sync.answer)).catch(() => {})
} catch {
  return 'the composer had already settled'
}
return null
```

`answer()` 的**异步拒绝**被静默吞掉，然后返回 `null` → 记 `attempted`、上报 `applied` → 宿主清掉 decision（`mirror.js:78`）。**同步 throw** 却走 `'the composer had already settled'` 分支。当前 shell 的 `answer()` 只会在"已 settle"时拒绝，所以今天吞掉是对的——但代码无法区分"已 settle（成功）"与"真实失败（传输/网关错误）"。

- **一旦 shell 让 `answer()` 因其它原因拒绝**：镜像上报虚假 applied → 宿主清决策 → 桌面 composer 永久等待、手机决定被丢弃，**零痕迹**。
- **修好判据**：给 `answer` 的拒绝分类——仅"已 settle"类按 applied 处理；其它拒绝按 error/skipped 上报、不记 attempted、不让宿主清决策。测试断言两种拒绝路径上报不同。
- **与自身注释矛盾**：同步 throw（已 settle）当失败、异步 reject（可能真实失败）当成功——两条路径的语义正好接反了。

### N3（S2，已验证）— 镜像轮询无超时 + `inFlight` 死锁

`readSync` 的 fetch 无 `AbortSignal`、无超时。若宿主接受连接但不响应，`readSync` 永不 resolve → `inFlight` 永久为 true → 后续每个 tick 在 `client.js:987` 直接 return，**镜像永久停摆**，只能刷新复活。这是"轮询失败是否会静默死掉"的直接回答：在连接挂起这类失败下会。

- **修好判据**：`readSync` 加超时（`AbortSignal.timeout`），超时上报 `error` 并释放 `inFlight`；测试注入永不 resolve 的 fetch，断言下一 tick 仍能轮询。

### N4（S2，已验证）— 旧宿主 404 时镜像静默空转

`readSync` 对 `!response.ok` 直接返回 `null`，镜像每秒静默轮询、无上报。卡片侧对同一 404 有 `hostOutdated` 文案（`client.js:556-559`），镜像侧没有。版本漂移（"只刷页面不更新宿主"）是代码自己预期过的场景，镜像却完全静默。

- **修好判据**：`readSync` 区分 404，首次上报一次 `error`/`unsupported` 并降频/停止。与 N3 同属 `readSync` 改造，可合并修。

### N5（S2，已验证行为/推断影响）— 镜像覆盖正在输入的桌面草稿

手机在 head start 之后才可答，而桌面 composer 在手机可答期间**保持打开**（`client.js:867-872` 注释确认）。用户正在桌面打字时手机按下 → 镜像直接 `pending.answer()` → composer 以手机答案关闭，**未提交草稿静默丢失**。head start 只覆盖"还没答"，不覆盖"正在答"。

- **这是产品决策**：是否应在 apply 前检查 composer 有无非空草稿/被聚焦，有则挂起镜像并让用户在卡上确认；或至少上报 `skipped: desktop composing`。建议作为第 4 优先与用户对齐。

### N6（S2，待验证）— `steer` 不证明兑现（R18 同构）

`agent.steer(message)` 返回 void。`boundaries.md` 已记录其契约："取消或卸载可能丢弃未消费的 steering"。与 R18（`followup` 排队未兑现）是同一道题：**同步调用不证明兑现**。R18 的修法是"换 API + 每分支一行日志"，steer 也有日志（`logInstructionSteered`）——但日志只说明"走了哪条路"，不证明"进到了轮里"。

- **真机上 R18 是这么丢的**：通知被消费、卡变执行中、toast 说已发送，而那一轮永远没来。steer 有同样的静默失败面（driver 在 step 边界之间被卸载/取消）。
- **修好判据**：真机验证 G7——运行时回复，确认那句话进到当前轮且对话记录可查；若有丢失，需要与 followup 相同的"兑现确认"信号（或至少在诊断里给出可查的迹象）。

### N7（S2，待验证）— `agent.status === 'running'` 判据的契约

#50 的分支在 `agent.status === 'running' && typeof agent.steer === 'function'` 上。测试桩只用 `'idle'`/`'running'` 两个值，且 `agent.status` 的完整枚举未在仓库内确认。若某 harness 版本把"运行中"叫别的值（或 agent 对象没有 status），走 `followup` → 重蹈 R18。**fallback 是刻意的**（老版本保持旧路径，见 result-run 用例），但依赖"status 准确反映是否在跑"。

- **修好判据**：在部署日志里确认实际出现的 status 值集合；若出现第三个值，需决定它属于哪条路。

### N8（S3，已验证）— `owns()` 不查 `orphaned`

`activity.owns()` 只遍历 `activities`，不查 `orphaned`（记录被 LRU 淘汰时 handle 暂存处）。极端场景：64 会话并发、某记录被淘汰后 handle 进 orphaned，此时结果卡的 `retract()` 查 `owns(handle)` 返回 false → 改写那张已被接管的卡为"该请求已失效"。活动卡无控件，press 本身不会来，所以触发需要"adopt 后记录被淘汰 + 该卡又被改写路径碰到"——概率极低。

- **修好判据**：`owns` 同时查 `orphaned`（`claimedHandle` 只该在记录重建时消费，这里只读即可），或补一条 65 会话的用例断言淘汰后 `owns` 仍为 true。

### N9（S3，已验证）— adopt 时 sending 在途 → 一次回复两张消息

`adopt` 拒绝在 `record.sending === true` 时接管（防 handle 落地冲突），此时 `results.send()` 走 fallback 改"已收到指令"，而活动卡稍后 deliver 一张新卡——**一次 press、两张消息**。这正是 #47 想消灭的形态，但在"回复时活动卡正在为该 session 发首卡"（手机优先刚生效、首卡在途）时会重现。代码注释明确接受（"the honest card for a session whose first card is still being created"），所以是已知取舍；记录下来供日后评估频率。

### N10（S3，已验证）— 诊断改写行未防抖

`3ababe8` 用 `noteSkip` 修了 skip 行每 250ms 洪泛的问题，但**改写行**（`活动卡：改写...`，`activity.js:714`）仍每次 update 无条件打一行。live 卡每 250ms flush 一次 → 单会话 4 行/秒；64 会话全活时 256 行/秒写入 debug 文件。skip 是"重复记录同一个未发生的决定"，改写是"记录每个真实动作"——两者性质不同，但 debug 文件在长任务+多会话下确实会显著增长。

- **修好判据**：与 skip 同样的去重是否合理需权衡（改写是真实事件）；至少确认 debug on 时文件增长可接受，或在文档说明量级。

### N11–N16（S3，已验证/待验证）— client 端杂项

见 C6–C10 对应条目：卡片轮询乱序覆盖、剪贴板拒绝未处理、adopt 失败清空表单、镜像无退避、订阅 disposer 丢弃。均为低风险改进项，C10 需确认 shell 的 fiber 清理行为。

### N17（S3，已验证）— `isClosed` 死参数

`escalation.js:52` 的 `isClosed = () => false` 从未被调用（`escalate` 用的是模块内部 `closed` 标志），`index.js` 也未传入。删掉或改造成真参数。

### N18（S3，推断）— reply 后 250ms 窗口内按 work 表单

adopt 后活动卡在 250ms 内把控件清掉（`buildView` 无 forms）；在此窗口内若读者再按 work 表单，`work.handleAction` 会启动新会话，但 `aftermath(handle)` 查 `cardOf` 找不到 notice（reply 已删）→ 卡上无"已开新会话"提示。极端双按边缘。

### N20（S1，已验证）— 提交污染：HEAD `ef92606` 缺 `'max-tokens'`，干净 HEAD 上测试实测变红（已由 `bea0c29` 修复，见 §九）

**这是本次评审最重要的发现，先说结论：**

- `git show ef92606:results.js` 显示 `const UNFINISHED_REASONS = new Set(['error'])`——**缺 `'max-tokens'`**。
- 在 `git archive HEAD` 的干净副本上跑 `unfinished-run.test.mjs`：**变红**（"a run cut off by its output ceiling gets a card too"，`0 !== 1`）——max-tokens 中断的轮次在 HEAD 上**不发结果卡**，#53 的承诺丢了一半。
- 工作区文件是正确的 `['error', 'max-tokens']`（`git status` 的 `M results.js` 即源于此）。**提交工作区即可修复。**

**成因**（时间线还原）：评审期间工作区被并发编辑（#55 作者）+ 测试质量子代理在原工作区做负向对照（把 `['error','max-tokens']` 改成 `['error']` 跑测试）。某个时刻并发编辑者 `git add` + `amend`，恰好把对照用的 `['error']` 版本卷进了 `ef92606`；子代理随后把工作区恢复为正确值，但 HEAD 已定格。

**为什么是 S1**：这是"**把错误结论写进提交**"——`ef92606` 声称是 #53 的合并分支，实际跑不过自己的测试；若直接发布（`npm run e2e` 的 pack 不跑单测、`verify` 只在 push/PR 时跑），用户会拿到 max-tokens 中断不发卡的版本。**CI 的 `verify` job 跑 `npm test`，只要 ef92606 上 PR/CI 就会拦下来——所以它还没有离开本机，是最好修的时候。**

**修好判据**：提交工作区的 `M results.js`（恢复 `['error', 'max-tokens']`），然后在干净 HEAD 上 `npm test` 全绿后再推送。

**教训（写进报告供下一次）**：**负向对照绝不在原工作区做**。本次父侧在 `git archive` 的隔离副本上做对照（零污染），子代理在原工作区做（卷进了提交）。这个仓库的测试正是防"改错方向"的护栏——但护栏只在代码到达 CI 时生效，提交前的污染要靠隔离工作流防。

### 时序 flaky 审计

套件 238 用例 77 秒。大量固定 `sleep(1100/1200)` 等 1 秒冷静窗口/升级定时器。子代理的 top 5（按暴露度）：

1. **`unfinished-run` / `fold-scope` 的 `takeOverFromThePhone`**：`sleep(1100)` 等 1000ms 桌面专享定时器（margin≈100ms），5+5 个用例依赖；失败是级联式（`lastDelivered()` 取空 → `clickCard(undefined)` → 后续断言全在错误状态失败，读起来像无关失败）。
2. **`unfinished-run` 的 `stoppedRun`**：`sleep(1300)` 等 1000ms 冷静窗（margin≈300ms），5/5 用例依赖。
3. **`result-run` 的 `afterARun`**：`sleep(1400)`（margin≈400ms），13 用例中 9 个以此为基座；400 步 PLAN 的 `runGroups` 是全套件最重的同步渲染，负载下最可能把定时器回调链推迟。
4. **`fold-scope` 的 `settle = sleep(400)`** 等 250ms `REFRESH_MS`（margin≈150ms）；失败读起来像"折叠缺失"（折叠只在 settled 时渲染），最迷惑。
5. **`client.test.mjs` 的 `sleep(1100/2500)`** 等 mirror 客户端 1000ms 轮询——轮询每次完成后重 arm，无到期顺序保证，`sleep(2500)`"等两个 tick"是套件里最真的节拍耦合等待。

缓解因素：node --test 每文件独立进程 + 定时器同相位按到期顺序触发，所以比 94 个固定 sleep 的表面数字稳。但负载机器上 margin≤150ms 的用例（#1/#4）仍可能翻。**推荐模式**：`result-run` 的 `phoneHoldsIt`、`priority` 的 `cardsArrived` 已用 `for (attempt…) { if (condition) break; await sleep(50) }` 轮询到条件成立——应推广到 #1/#2/#3 的基座函数。
