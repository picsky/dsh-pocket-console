# 0021 — 会动的那张卡，就是你按的那张

**Status:** accepted.

## Context

手机上有两张卡在讲同一个会话：`DSH 执行中`（过程）和 `DSH 结果`（答复 + 回复框）。它们各由一半代码
管，两张卡之间**没有任何联系**——`results.js` 不认识 `activity`，`activity` 也不认识 `results`。

于是回复之后发生的是：

```
[DSH 结果 · my-app]   ← 你在这张卡上打字、提交
  **已收到指令**，已排入该会话。        ← 它只变了这一行
[DSH 执行中 · my-app]  ← 一轮真在跑，但它出现在**另一条消息**上
```

**你按的那张卡不动，动的那张卡你没按。** 用户的话是判据：

> 我倾向于就用我操作的卡片直接变。……回复以后，原来的结果卡变为新的执行中卡，执行完毕新的结果卡要独立。

另一半也是他说清楚的：**新结果必须独立**。也就是说不能反过来把结果改写进执行中卡里——那两个角色
是两件事：一张是"现在在跑什么"，一张是"跑完了，你要不要回一句"。

## Decision

**回复被接受时，把那张消息直接交给执行中的卡。**

`results.js` 在把指令交给会话之后调用 `activity.adopt(session, handle)`：这张消息从这一刻起就是**这个
会话的执行中卡**，由 `activity.js` 继续改写（状态行、时长、最新片段、结束后的折叠）。原来那套
"改写成已收到指令"退化成**降级路径**，只在没装 activity 模块的组装里生效。

配套两条：

- **`adopt` 会拒绝"发送中的卡"**。第一条执行中卡还没拿到消息 id 时，抢占一个 id 只会让那次发送的
  应答落在刚接过的消息上。拒绝时说清楚，回复路径照旧走自己的改写。
- **执行中卡占着的消息，别的路径不许再改**（`activity.owns(handle)`）。结果卡的"这张卡已失效"分支
  原本会改写"按下按钮的那条消息"——而现在那条消息就是正在跑的那张卡。

**执行完毕的结果卡仍然是新的一条消息**（`create` 会响、`patch` 不会）。所以：

| 时刻 | 消息数 |
|---|---|
| 第 1 轮：执行中卡创建 | +1（响） |
| 第 1 轮结束：结果卡创建 | +1（响） |
| 你在结果卡上回复 → **它变成执行中卡** | **+0** |
| 第 2 轮结束：结果卡创建（独立） | +1（响） |
| 之后每一轮 | **+1** |

即：第一个回合 2 条，**从第二个回合起每回合只多一条**。这不是省出来的——它和原来一模一样，只是
"执行中"落在你手里的那张卡上，而不是落在旁边那张你没碰过的卡上。

## Consequences

- **卡片的脸会变**。接过来之后标题是 `执行中 · <项目>`，正文是状态行 + 时长 + 最新片段；答复正文和
  「思考过程」折叠在执行期间不在卡上。这是刻意的：**活着的卡不折叠**（[0017](0017-the-result-card-carries-the-run.md)），
  折叠在那一轮结束后随记录一起回来，而刚结束的那一轮在 `adopt` 时就已经折进记录里了（`closeTurn`）。
- **滚动记录的顺序变了**。第 1 轮那张执行中卡从此再也不会被改写——它的记录停在第 1 轮，成为一条留档。
  一个会话的卡片序列读起来是：第 1 轮的执行中卡、第 2 轮的执行中卡（前身是第 1 轮的结果卡）、……
  每一轮都有一张自己的卡。
- **答复正文的去向**。答复在执行期间离开卡面（活着的卡不折叠），它和那一轮的过程在执行记录里；那一轮
  结束、卡片冻结时，折叠把它们一起放回来。**前提是 activity 模块跟过这一轮**——它在 `turn/start` 建档。
  进程在这一轮中途才启动（重启后回复一张恢复出来的卡），或这个会话的记录被 64 条的容量挤掉时，这一轮
  只有 run-record 有、activity 没有，那么**接过来的卡上那份折叠就丢了**（答案在会话里还在，手机上不
  在）。这条不做隐式补偿：在那两种情况里宁可少一张折叠，也不编一份出来。它会写进调试日志：
  `活动卡：接过消息 … 时没有「…」这一轮的记录`。
- **这条设计押在一个平台事实上**：**表单被提交过的卡片，之后还能继续 `patch`**。真机实测过（一张带
  表单的卡连续改写 90 次全部 `code=0`，且控件一直在卡上，提交之后仍在继续）。**按钮被按下之后的改写
  仍未验证**——所以需要就地变的卡一律用**表单**（结果卡就是表单），审批卡与提问卡用按钮，但它们
  从不需要事后改写。
- **降级是显式的**。组装里没有 activity 模块时，回复卡回到"已收到指令"，执行中的过程仍然另发一张卡
  （每一个更早的版本都是这样）——不是静默少了个功能，而是少了一个模块。

## Alternatives

**用执行中卡承载结果**（跑完把过程卡改写成结果卡，一条消息到底）。否决：用户明确要求**新结果卡独立**。
而且飞书只有 `create` 会响，那条路会让"跑完了"这件事完全静默——这个人正是不在桌面前才在手机上看。

**把旧执行中卡删掉。** 否决：它现在是第 1 轮的留档（折叠里有那一轮的过程），删掉是丢信息；而且删除
消息是另一条平台路径，这次没有必要碰。

**让结果卡就地把过程写在自己身上，不认领**（即执行中也画在结果卡上，但两张消息都在）。否决：那就是
现在这个 bug 的另一种写法。

## What would reopen this

- 真机上出现"回复之后卡片没变"——那说明**表单提交后再改写**在更严的条件下会被冻结（当前只在一种
  表单卡上验过），这个设计的立足点就没了。
- 真机上出现两张执行中的卡同时动（`adopt` 没接管成功，而执行中卡另发了一张）。
- 观感上"答复在执行期间看不到"被认为是缺陷（那要把刚结束那一轮的答案留在脸上，而不是只留在折叠里）。
