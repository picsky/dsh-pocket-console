# 0018 — 常驻状态板是一张置顶卡，而且是一张没有控件的卡

**Status:** accepted.

## Context

会话状态目前只能靠**卡片路过**：审批卡、结果卡、活动卡。它们都是事件驱动的——只有在插件
有话要说的时候，手机才会知道任何事。人想知道"现在到底什么在跑"，唯一的办法是等一条通知，
或者回桌面。

"不主动推状态"是一条已有的决定（[0015](0015-desk-presence-is-the-gateways-request-id.md)）：
一个开着的页面会把"人在手机边"这个真实状态盖掉。所以需要的不是**推送**一个新的状态面，而是
一个**人主动去看**的面——它常驻在某处，不叫人，但随时在。

这就要求飞书有一个"写一次、长期挂着、还能改"的位置。本次把飞书的可用面全部实测了一遍，结论
和文档里写的**不一致**，而且本文档自己此前有一条**错的**结论。

### 实测（真实租户、本应用凭据、2026-09-20）

| 面 | 结果 |
|---|---|
| `POST /im/v1/pins`（置顶一条消息） | ✅ `code=0` |
| `DELETE /im/v1/pins/:message_id`（取消置顶） | ✅ `code=0` |
| `PATCH` 一张**已经被置顶**的消息 | ✅ `code=0`——置顶不冻结内容 |
| `GET /im/v1/pins`（列置顶） | ❌ 需 `im:message.pins:read` |
| 读回消息 / 聊天历史 | ❌ 需 `im:message:readonly` 或 `im:message` |
| 聊天信息、群公告、建群 | ❌ 需 `im:chat*` |
| 表情回应（读/写） | ❌ 需 `im:message.reactions:*` |
| **cardkit 卡片实体**（`POST /cardkit/v1/cards`、流式更新、全量替换） | ❌ 需 `cardkit:card:write` |
| `im/v1/messages` 的 `create` 带 `config.streaming_mode: true` | ⚠️ `code=0`，但**服务端流式更新在 cardkit 侧**，所以这是静默无效 |

**根因是一条总规律：这个应用只能往对话里写，一个字都读不回来。** 所以任何"先查一下自己之前
发过什么"的设计都不成立，一切状态必须由插件自己记住。

顺带纠正两处：

- `internal/boundaries.md` 原写"pin 是内测能力、私聊支持未文档化"并**据此拒绝**。这条是错的，
  从未实测。置顶不需要任何新权限，私聊也支持。
- 流式卡片这条路线需要 `cardkit:card:write`，本应用没有。而 `streaming_mode` 在 `im` 侧的
  `create` 上**不报错也不生效**——静默无效比明确拒绝更坏，不能依赖它。

## Decision

**常驻状态板 = 一张被置顶的卡片，纯展示、无任何控件、每个 profile 一张，其 `message_id` 由插件
自己持久化。**

每条都值得单独说：

- **置顶，因为它是唯一可用的常驻面。** 群公告、聊天信息、机器人菜单、`open_url`/webview 要么
  缺权限、要么要求插件自己提供一个可访问的网址（等于开端口，与
  [0007](0007-prepend-and-race-the-desktop.md) 的前提冲突）。置顶是唯一一个"写一次就长期存在
  于对话顶部、且不需要新权限"的机制。
- **没有控件，因为这是它还能持续更新的唯一办法。** 一条被交互过的卡片不能被平台改写，而"持续
  反映状态"是这块板的全部工作（下面「待验证」)。控件与可编辑性二者只能取一个，取可编辑性。
- **它不是新的推送面。** 置顶不替插件叫人，插件也不为更新状态板发通知——更新是 `patch`，本来就
  静默。板子只回答"人主动去看"的问题，不改变 0015 的结论。
- **每个 profile 一张，`message_id` 进持久化存储。** 因为读侧全堵（列不出自己的置顶），插件必须
  自己记住它。存储沿用已有的 `pocket_console` 域（`notice-store.js` 用的同一个）。**已知代价**：
  容器一旦丢失（换机、清 profile），置顶卡会成为孤儿，只能人工取消置顶——插件无法发现它，也
  无法清理它。
- **不用 cardkit 流式卡片。** 缺 `cardkit:card:write`。若部署方补上该权限，流式卡片是更好的形态
  （服务端增量更新、有 loading 态），这条决定应当重开。

## Consequences

- 手机端有了一个"不看桌面就能看状态"的位置，而且它不响。
- **它不能承载交互。** 于是"用置顶卡当常驻入口"这条路被否掉了：一个能从状态板发起新任务的按钮
  会把板子冻在第一帧，之后永远不再更新。要开新任务，仍然走一张自己的卡。
- 状态板与"每次运行一张卡"是**两件独立的事**：板子**不减少**每次运行的卡片数。减少卡片数要靠
  另一条决定（把"新任务"折进结果卡），不要把它和板子混在一起谈。
- 插件对置顶卡的生命周期只有一半控制权：能置顶、能改、能取消置顶，但**发现不了**它。

## 待验证（写进 `internal/verification-checklist.md`）

- [ ] **卡片被交互过之后是否真的不能编辑**（`已验证` 的是"文档这么说"；真实租户上未测）。
      这条决定"状态板不能有控件"这个论断，必须实测。
- [ ] 置顶卡在**手机端**的具体观感：是不是一条横幅、要不要点开、会不会被新消息刷掉。
      这是本决定的产品前提，插件侧测不到，只能人看。
- [ ] 置顶**之后**再编辑，置顶位置是否保留。
- [ ] `POST /im/v1/pins` 对**机器人自己发的**消息是否稳定（本次一次成功，样本为 1）。

## Alternatives

**把状态板做成一张普通的、不置顶的卡。** 否决：它会往下沉。每次运行的消息都比它新，人得翻聊天
记录找它——那和"没有板子"差不多，只是多了一条消息。

**让状态板带一个"刷新"按钮，按下时重发一张新卡并重新置顶。** 否决：每次刷新都是一次**通知**，
而这块板存在的理由是"不叫人"；何况重发会留下一条旧卡的尸体。

**用 cardkit 流式卡片做板子。** 目前不可行（缺权限），但**这是权限补上后的正解**，故列入重开条件。

**用一个 `open_url` 按钮指向本地页面。** 否决：等于开一个入站端口，与 README 的"没有入站监听"
和 [0007](0007-prepend-and-race-the-desktop.md) 冲突。

## What would reopen this

- 部署方补上 `cardkit:card:write`：流式卡片能同时给出 loading 态与增量更新，板子可以更好。
- 实测发现"被交互的卡仍可编辑"：那么状态板可以带控件，也就不再需要为开新任务单发一张卡。
- 飞书放开 `im:message.pins:read`：插件能列出并认出自己的置顶卡，孤儿问题消失。
