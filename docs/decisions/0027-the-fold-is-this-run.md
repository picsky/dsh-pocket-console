# 0027 — 折叠只放这一轮

**Status:** accepted.

## Context

[0022](0022-the-fold-is-one-turn-and-marks-what-you-said.md) 让执行中卡的「本次执行过程」折叠保留**"你回复的那一轮 + 这一轮"**。保留那一轮的理由是：卡片被回复后就地变成运行卡，正脸换成运行状态，不留它，读者按下回复时正在读的那段答复就从手机上消失了。

真机上跑起来之后，读者（部署者本人）报的是另一件事：**执行结束后，这个折叠总是带着上一轮**。用部署里同一份 `activity.js` 回放真实会话事件流，量出来的是：

| 轮结束 | 折叠 | 大小 |
|---|---|---|
| 一轮（本进程里该会话的第一轮） | 1 轮 | 5787 B |
| 第二轮 | 2 轮（上一轮 + 本轮） | 11533 B |
| 第三轮 | 2 轮：上一轮 **5739 B** + 本轮 **2175 B** | 7921 B |

三件事随之清楚：

1. **上一轮占了折叠的 72%**，而它是读者刚在上一张卡上读过、也已经回复过的内容——折叠的标题却是「本次执行过程」。
2. **两张卡的折叠口径不一致**：结果卡走 `run-record.js` 的 `readRun`，范围是"从人上次说话算起"的**一轮**；执行中卡是两轮。同一时刻同一个会话，读者看到多少历史取决于他打开哪张卡。
3. **边界认不出来**：两轮之间是裸 `---`，而模型自己的 markdown 也常写 `---`。实测同一份数据按 `---` 切会切出**三段**，第三段其实是模型写的一条横线。

另外发现两处与"历史"绑在一起的事实：轮内非人话的 `user/message`（`subagent-settled`、`agent-message`）也画组边界且只保留最新一组，所以带着 `**你**：` 的那一组**可能被丢掉**（一个轮内出现两次就够）；而 `run-record.js` 里为"冻结卡要保有序列"准备的 5 轮历史（`TURN_HISTORY = 5`、`read()`、`mergeByKind()`）**没有任何调用者**——那份能力谁也没拿到，却顺带让结果卡上的"省略 N 字节"把**被丢弃的整轮**也算了进去（卡片显示的是一轮，报的却是好几轮的损失）。

## Decision

**折叠只放这一轮：从这个人上一次说话算起（含其间自动续跑的内部轮），到本轮结束。上一轮不进折叠。**

- **边界只有一处：人说话**（`source.kind === 'user'`）。`turn/start` 不是边界（一句人话可以跨好几个 turn：子代理结算、重试、排队续跑都开 turn），非人话的 `user/message` 也不是边界（那是"这一轮被告知的东西"）。
- **`activity.js` 不再有历史**：`TURN_HISTORY`、`record.turns`、`archiveProcess` 的归档逻辑删掉，换成 `clearRun`（清空本轮）。`detailsFor` 渲染一个组，**因此不再有 `---` 分隔**。
- **两条折叠同一口径**：结果卡的 `readRun` 本来就是这一轮，活动卡向它对齐。
- **`run-record.js` 里那份没人读的历史删掉**：`TURN_HISTORY`、`read()`、`mergeByKind()`、以及只被 `read()` 返回的 `entriesLost` 一并移除。`dropped` 随之只描述**这一轮**丢掉的东西——这是结果卡上那个数字本来就该说的意思。

## Consequences

- 折叠的字节量：实测那一轮从 7921 B 降到约 2175 B。
- **代价（明确接受）**：被回复过的那张结果卡的正脸已经变成运行卡，所以**上一轮的答复不会再从折叠里回到手机上**。这是 0022 保留那一轮的唯一理由，由产品决定推翻（0022 的 Alternatives 里记着读者最初就要"严格本轮"）。
- **不会再出现"两条卡各带一段历史、彼此重叠一轮"**：同一轮只出现在报告它的那张结果卡里。
- 读者不会再看到两段之间那条 `---`，也就不会再把它和模型自己写的横线混起来。
- 轮内出现子代理结算/agent 消息时，`**你**：` 那一行**不再可能被挤掉**——组不再在那些事件上切开。
- 结果卡上的"省略 N 字节"变小（且更准）：被丢弃的整轮不再计入。实测常用路径下它是 0，看不出差别；长会话里有差别，方向是报得更少而不是更多。
- 卡片的编辑次数与消息数**不变**。

## Alternatives

**保留"上一轮"，但只用一条引用（只保答复、不保过程）。** 这是本次分析里的推荐方案 C：信息不丢、历史感也没有。被读者否掉的理由是**简单**——他只要"本轮"，一条引用仍然要在卡片上多一种区块、多一套裁剪与预算规则。记在这里，因为它是将来若有人抱怨"答复消失"时的第一选择。

**只保"上一轮"的答复而删掉它的过程。** 同样是 C 的变体，评估结果同上。

**保留两轮但给每段加标题（"上一轮 / 本轮"）。** 解决"分不清哪段是哪段"，但没解决重复，也没解决两张卡口径不一致。否决为当前做法。

**把两份记录合成一份（活动卡直接渲染 `readRun`）。** 更彻底，[0022](0022-the-fold-is-one-turn-and-marks-what-you-said.md) 就把它记为"下一步"。这次**口径**对齐了，实现仍是两份：合并要先动 `index.js` 的装配顺序（`activity` 在 `runRecord` 之前创建），并且与本决定无关——决定是范围，合并是结构。

## What would reopen this

- 读者抱怨"我回复时读的那段答复不见了，手机上没有"——那就回到引用式（Alternatives 第一条）。
- 手机端出现"一轮的答复被截断成两段、看起来像两轮"——那说明同一个 run 里仍然有东西在切组，边界要看。
- 一个 run 真的长到折叠放不下（`PROCESS_BUDGET` / `CARD_TEXT_BUDGET` 开始丢内容）——那是"折叠装不装得下"的问题，不是范围的问题，但会重新引出"要不要按轮分组"。
